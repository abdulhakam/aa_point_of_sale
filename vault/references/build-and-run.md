All four run onWindows; the `.BAT` files are the supported entry points.## Start order```text1. backend\DEV.BAT                (development)   PocketBase :8090  +  Next.js dev :3000   — or —1. backend\RUN NEXTJS.BAT         (production)    PocketBase :8090  +  Next.js start :3000   — or —1. backend\RUN SERVE.BAT          (static)        PocketBase :8090  +  http-server :30002. trailbase\RUN.BAT                              TrailBase :4000  (serves the APIs *and* the app)```Steps 1 and 2 are independent stacks — you can run the legacy pair, the new pair, or both atonce. Ports do not collide. Port table: [[environment]]. The guest app has no separate process and**no separate port**: it is a component of the single TrailBase server, served from `:4000`([[runtime-js-guest-platform]]).## Legacy pair (production)### `backend\DEV.BAT` — development```batstart "" .\pocketbase.exe serve --devtimeout /t 1 >nulcd ../frontendstart "" npm run devtimeout /t 3 >nul```Starts PocketBase in dev mode, then Next.js dev mode. The `start` calls are non-blocking, sotwo windows appear. The `timeout` lines are the only synchronisation — PocketBase's admin UI isat `http://127.0.0.1:8090/_/`. Notes: the trailing `start "" http://127.0.0.1:3000` line iscommented out (`@REM`), so the browser is not opened automatically.### `backend\RUN NEXTJS.BAT` — production-styleSame shape, but `pocketbase.exe serve` (no `--dev`) and `npm run start` (the Next.js productionserver, which requires a prior `npm run build`). Opens `http://127.0.0.1:3000` after a 3-secondwait.### `backend\RUN SERVE.BAT` — static serve`npm run serve` → `http-server ./out/ -p 3000`, i.e. serving a **static export** rather thanthe Next.js server. This needs `out/` to exist; `next.config.js` does not set`output: 'export'`, so check that a static export is actually what you want before using it.### Frontend build commands| Command | Purpose ||---|---|| `npm run dev` | dev server || `npm run build` | production build || `npm run lint` | ESLint || `npm run build:standalone` | `next build` then three `robocopy` calls into `../standalone` — the deployable bundle || `npm run storybook` | component workshop on `:6006` |## New pair (experimental)### `trailbase\RUN.BAT````batif not defined DEPOT set "DEPOT=traildepot"if not defined ADDRESS set "ADDRESS=127.0.0.1:4000"set "ADMIN_USER=admin@localhost"set "ADMIN_PASSWORD=administrator-0ne"```What it does:1. **First run only** (when `%DEPOT%\data` does not exist): calls   `trail user change-password %ADMIN_USER% %ADMIN_PASSWORD%`. That command initialises the   depot from `config.textproto` + `migrations/`, creates the admin user **and** sets the fixed   password — all before a server starts, so nothing races initialisation. If it fails it   prints a warning with the manual command instead of dying.2. Starts the server with `start "" trail "--depot=%DEPOT%" run --address=%ADDRESS%`.3. Polls `netstat -a -n -p tcp | findstr %ADDRESS% | findstr LISTENING` up to 30 times   (~30 s), then opens `http://%ADDRESS%/_/admin/`. If nothing is listening it prints a   warning telling you to check the TrailBase console — rather than opening a tab that cannot   be reached.Environment overrides, each quoted so no trailing space is kept:```batset "DEPOT=C:\some\depot" && RUN.BATset "ADDRESS=127.0.0.1:4001" && RUN.BAT```⚠️ **Delete `traildepot\data\` before a re-scaffold** if you previously ran an older version ofthis scaffold. Refinery silently *skips* a migration whose checksum changed, so a stale depotkeeps the old schema. See [[trailbase-stale-depot-skips-migration]].First-run credentials: `admin@localhost` / `administrator-0ne`. Change them before real use:```shtrail --depot=./traildepot user change-password admin@localhost <pw>trail --depot=./traildepot user change-email   admin@localhost <email>```Other useful CLI commands:| Command | Purpose ||---|---|| `trail --depot=./traildepot run` | plain start (no credential bootstrap, no bind override) || `trail --depot=./traildepot schema items` | export a record API's JSON schema || `trail --depot=./traildepot schema invoices` | `invoices.type` is `{"type":["null","integer"]}` || `trail --depot=./traildepot user change-password …` | set a password without running the server |Installing the binary, once: `iwr https://trailbase.io/install.ps1 | iex` (Windows) or`curl -sSL https://trailbase.io/install.sh | bash` (Unix).The Node `frontend-ssr` process that used to sit here was removed on 2026-09-27([[guest-ui-is-a-direct-shift-of-legacy]]); its `RUN.BAT`, `.env` and `npm run smoke` no longerexist. The new frontend is the guest-WASM platform below.## Guest-WASM platform (the new frontend, experimental)The depot is assembled from the checked-in sources and the built component by two `.bat` files, then servedby TrailBase itself ([[runtime-js-guest-platform]]):```powershell# 1. reset traildepot/ from the checked-in sources (wipes the database)trailbase\clear_db.bat# 2. build the Rust host (Rust + wasm32-wasip2 + QuickJS via rquickjs + minijinja), copy it intrailbase\build.bat            # -> traildepot/wasm/tb-ah-run-js.wasm# 3. start the servertrailbase\RUN.BAT              # trail --depot=traildepot run --runtime-root-fs=traildepot/runtime````RUN.BAT` runs 1 and 2 automatically if the depot is not prepared (no `traildepot/config.textproto`or no wasm component).- `--runtime-root-fs=traildepot/runtime` is **load-bearing**: it is the WASI sandbox root, so the  app's `app/` and `ahscripts/` live under it. It points at the **generated copy**, not at  `trailbase/runtime/` — so after editing the app, run `clear_db.bat` (or copy the tree) or the  change does not reach the server. Keeping it a subdirectory (not the depot root) keeps the  depot's `data/` and `secrets/` out of the guest sandbox  ([[trailbase-guest-wasm-runtime-defaults]]).- `trailbase/` is the source of truth: `config.textproto`, `metadata.textproto`,  `migrations/`, `host/` = the compiled Rust crate, `runtime/` = the editable app,  `tools/` = the harnesses. `traildepot/` is generated from it.- Do **not** pass `--aot`: it doubles the size and is 2.3× slower to cold-load  ([[trailbase-guest-aot-startup-cost]]).- The Phase-0 spike guest is **gone**: `guests/` was deleted on 2026-09-28, so the port `4001` depot no  longer exists ([[runtime-js-guest-platform]]).- Ports, depot paths and the harness list are in [[environment]].### Verify**Deploying an app change to the production depot (the safe path).** `clear_db.bat` wipes`trailbase\traildepot\data` — the 60,245 imported production records — so it is **not** the way topush an edit. The server reads the *generated* copy under `traildepot\`, so sync the source acrossand restart:```powershellrobocopy trailbase\runtime    trailbase\traildepot\runtime    /MIR /NFL /NDL /NJH /NJS /NProbocopy trailbase\migrations trailbase\traildepot\migrations /MIR /NFL /NDL /NJH /NJS /NPtrail --depot=traildepot run --address=127.0.0.1:4000 --runtime-threads=4 --runtime-root-fs=traildepot\runtime```- **The restart is required for anything under `app/lib/`.** Modules are loaded once per QuickJS  context and cached on `globalThis.__AA_MODS__`, so a new export only appears after a restart —  otherwise the screen fails with `not a function` / `cannot read property … of undefined`. Edits to  `app/views/*.html`, `app/public/**` and to `ahscripts/routes/_app/route.ts` hot-reload.- Sync `migrations/` too.
