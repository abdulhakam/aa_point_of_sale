## Completed since previous checkpoint

- Exercised filters on all **14** reports: APPLY with changed select/date/checkbox values and RESET on the
  page host, and the same filters replayed on the legacy route — **14/14 pass** (filter changes the result,
  filtered result identical to legacy, RESET returns to the default).
- Benchmarked the two implementations on the live dataset — see the resolved
  [[Issue — Declarative pages ship whole views and are slower than server rendering]]:
  - **Server-side** (median of 5, gzip): **270 ms → 44 ms (~6× faster)**; transferred bytes
    **1.13 MB → 124 KB**; wire size 5–9× smaller for every report.
  - **End-to-end** (in-page time-to-ready, cache off, median of 2): page host faster on **10/12** reports,
    within 2–7 ms on the other two.
- Re-ran `npm run smoke` on the current working tree: **59/59**.
- Updated the performance issue to **Resolved**, closed TB-0008, and moved TB-0009 to Ready.

## Current verified state

- Page host and legacy routes produce identical rows and totals on live data, unfiltered, filtered, and with
  RESET — **14/14**.
- The page host is **faster than the server-rendered route** where it previously lost: the client does no
  report computation (`window.__page.computeMs = 0`) and the server serves the warm snapshot.
- Honest caveat: decoded JSON is larger than decoded HTML (JSON verbosity), but transferred bytes are much
  smaller because the endpoint is gzipped and the legacy HTML is not.
